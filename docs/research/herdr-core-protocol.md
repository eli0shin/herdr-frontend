# herdr-core client protocol

What herdr-frontend must do to be a second desktop client of herdr-core, side by side with Herdr
app on the same core, and a recommended Rust client design. Written so implementation tickets can
be cut from it without re-reading herdr-app.

## The rules in one place

These are the rules implementation tickets must not break. Each one is explained in a section below.

1. Use one framed connection: `hello {framed: true, generation: 1}`, then JSON-RPC on channel 0
   and streams on other channels. Get it from `hc connect`, the same way herdr-app does.
2. Return CREDIT on every stream after you have consumed the bytes. Reconnect when the connection
   drops, and use a fresh snapshot after reconnecting: `seq` restarts with each core process.
3. Subscribe before reading documents. Read them again after every `doc` event, every `missed`,
   and every reconnect.
4. The layout lives in the document named `herdr-app`, one per machine, under herdr-app's exact
   schema. Write it only with `doc.set` at the version you read. On `conflict`, read it again and
   replay your edit on the new copy. Never write back a document you only read.
5. Never write a document herdr-app cannot decode. Never drop fields you don't understand.
   herdr-app keeps unknown space and tab fields but drops unknown fields everywhere else, so
   data private to herdr-frontend can't live in that
   document.
6. Focus, zoom, active tab, settled tabs and recent spaces are this screen's alone. Keep them in
   herdr-frontend's own state, never in the shared document.
7. Labels follow herdr-app's conventions: `herdr.space`, `herdr.tab`, `herdr.seen`,
   `herdr.pinned`, `herdr.right-click` and `where`. A live terminal labeled `herdr.space` that is
   not in the layout gets placed into it by herdr-app.
8. Size goes to the most recently active non-observe viewer. Only take it for a pane the person
   is really using, and send RESIZE with the pane's current grid whenever a pane becomes active:
   the core applies the size the viewer last reported. Attach panes that are hidden or not focused
   with `resumed: true`, and reattach after a reconnect with `resumed: true`. Draw each terminal
   at the core's real grid, not your pane's.
9. Human keys go as DATA. Replies generated by the terminal engine go as AUTOMATIC_INPUT, but only
   when both `hello.features` and the attach reply say it is supported.
10. Check `generation == 1`, the minimum version, `methods` and `features` at connect, for the local
    core and for every machine.

## 1. Connecting

### Transports

| Transport | How | Notes |
|---|---|---|
| `hc connect` child process | stdin and stdout carry the same protocol as the socket (`core:schema/README.md` "Connecting"). | **herdr-app's choice** (`app:src/hc.rs:329`). It starts the core when none is running (`core:crates/herdr-core/src/client.rs` `connect_or_start`). It also applies the session, `HC_SOCKET` and config `socket` rules, and on macOS it repairs a core left from an earlier GUI login (below). `--session <name>` selects a session, like `HC_SESSION`. If startup fails, stderr carries one JSON object `{"error":{"kind","message","hint"}}`, which herdr-app parses (`app:src/hc.rs` `connect_error`). |
| Unix socket directly | `HC_SOCKET`, else config `socket`, else `$XDG_RUNTIME_DIR/herdr-core/<session>.sock`, else `/run/user/<uid>/herdr-core/`, else the session's state directory. Windows uses a named pipe. (`core:docs/security.md` "State and endpoints") | Lower overhead, but there's no autostart and no login repair, and the path rules must be reimplemented. Use it only behind the same transport trait. |
| Remote core through ssh | `ssh box hc connect`. The protocol is identical. | Possible, but herdr-app never connects to a remote core directly. It adds machines to the local core (§1.6). Do the same. |

macOS login repair: `hc connect` from a process in the GUI login may call `server.restart` on a
core that belongs to an earlier macOS login (`core:crates/herdr-core/src/platform/macos_session.rs` `repair`). That
is a planned restart: programs keep running and the next core adopts them. herdr-frontend inherits
this by using `hc connect`, exactly as herdr-app does. This is the core's own repair path; the
client never sends `server.restart` itself.

Finding `hc`: herdr-app checks settings, then `PATH`, then the login shell's `PATH`, then the
usual install places. A candidate counts only if `--version` prints `hc …` (`app:src/core_bin.rs`).
herdr-frontend needs the same search, because an app launched from the Dock doesn't inherit the
shell `PATH`.

Isolated cores, for tests: set `HC_SESSION=test-<x>` together with scratch `XDG_STATE_HOME` and
`XDG_CONFIG_HOME`. Stop it with `hc server stop` under the same environment
(`core:docs/security.md` "Sessions"; `app:src/hc.rs` ignored test
`two_app_viewers_answer_queries_without_idle_size_theft`).

### Handshake

A connection starts in **plain mode**: JSON-RPC 2.0, one message per line. The first request
should be:

```json
{"jsonrpc":"2.0","id":0,"method":"hello","params":{"framed":true,"generation":1}}
```

The reply is a single line: `HelloResult {generation, version, core {id, name}, framed, methods[],
features[], login_session?, keeps_running_after_logout?, logout_linger_user?}`. After that
reply, the connection is in **framed mode**. A `generation` other than 1 fails with
`unsupported_generation` (`core:crates/herdr-core/src/api.rs:195`). herdr-app omits `generation` and checks the
reply instead. Sending it is stricter and costs nothing.

The live core answered: version `0.1.22`, generation 1, features `framed, attach, events, status,
shell, resize_notifications, automatic_input, restart_environment, put_chunks`
(`core:crates/herdr-core/src/api.rs:17`), and 36 methods.

### Framing

Each frame is `[channel u32 LE][kind u8][len u32 LE][payload]`, with a payload of at most 16 MiB
(`core:crates/herdr-core/src/wire.rs`).

| kind | name | direction and payload |
|---|---|---|
| 0 | DATA | Channel 0: exactly one JSON-RPC message. Other channels: stream bytes. Viewer → core on an attach channel means human input. |
| 1 | CREDIT | Both ways: a u32 LE count of bytes the receiver consumed. |
| 2 | CLOSE | Client → core: empty, meaning detach or unsubscribe; the core answers with an empty CLOSE. Core → client: a JSON reason such as `{"reason":"exited","exit_code":0,"signal":null}`. |
| 3 | RESIZE | Viewer → core: u16 LE cols, then u16 LE rows. Core → observer: the same layout, only for observers whose attach reply confirmed `resize_notifications`. |
| 4 | FOCUS | Viewer → core: `1` gained, `0` lost. Gaining focus counts as activity (§4). It is forwarded to programs that enabled DEC mode 1004. |
| 5 | FACTS | Viewer → core: `Display` JSON `{fg, bg, cursor, cell}`, used to answer the program's color and cell-size queries. |
| 6 | AUTOMATIC_INPUT | Viewer → core: replies the terminal engine generated. They reach the program unchanged, but they are not activity: they never take the size and never reset the human quiet period. |

The core ignores unknown frame kinds and malformed CREDIT or RESIZE frames (`core:crates/herdr-core/src/server.rs`
`read_frames`). A consequence: sending kind 6 to a core that never advertised it silently
loses the input.

Channel 0 carries JSON-RPC in both directions. The core runs calls on it concurrently: a slow
`terminal.kill` or `terminal.wait` never holds up anything else. Ids are the client's. Requests
can be cancelled with `{"method":"$/cancelRequest","params":{"id":<id>}}`, which ends a
`machine.exec`, a `terminal.put`, or a `terminal.send` still waiting on a draft
(`core:crates/herdr-core/src/server.rs`). Replies the client never reads pile up to 64 MiB (`MAX_CONTROL`), after
which the core drops the connection, so the reader thread must drain without pause.

Errors are JSON-RPC errors with a stable `data.kind` and a `data.hint`:
`{"code":-32000,"message":"…","data":{"kind":"not_found","hint":"…"}}`. Kinds seen in the schema:
`invalid_params`, `not_found`, `machine_unknown`, `unavailable`, `finished`, `live`,
`needs_framed`, `name_taken`, `spawn_failed`, `invalid_template`, `config`, `blocked`,
`status_mismatch`, `cancelled`, `needs_target`, `conflict`, `needs_update`, `not_text`, `io`,
`edit_failed`, `already_added`, `unreachable`, `hc_missing`, `incompatible`, `internal`,
`unsupported_generation`, and `unknown_method` (code -32601). Match on `kind`, never on `message`.

### Flow control

- Every stream (attach or events) starts with 256 KiB of credit (`core:crates/herdr-core/src/wire.rs` `WINDOW`).
  The client returns CREDIT for the bytes it has **consumed**: written into the VT for an attach
  stream, or parsed for the events stream. herdr-app credits after `vt.write`
  (`app:src/terminal.rs` `ingest`). For the events stream it grants an extra 1 MiB at subscribe
  and then credits as it parses (`app:src/hc.rs:494`, `app:src/window.rs` event loop).
- A viewer more than 4 MiB behind (`MAX_PENDING`) gets a fresh repaint instead of the backlog. An
  events subscriber that falls behind gets `missed` with a fresh snapshot (§2.3). A stalled
  stream never blocks channel 0 or other streams.
- A stream is paused until its reply has gone out, so the `terminal.attach` or `events.subscribe`
  reply always comes before the first frame on its channel (`core:crates/herdr-core/src/server.rs`: `out.resume`
  after the reply). Because the reply and the stream frames are read by the same thread, the
  client must register the channel's route before reading on. Otherwise it buffers early frames by
  channel, as herdr-app does with `Routes.early` (`app:src/hc.rs`).
- When a program ends, its last output is delivered before the CLOSE.

### Reconnect

Losing the connection doesn't end the programs: the core restarts or updates and its holders keep
them alive. herdr-app's behavior is the baseline (`app:src/window.rs:819`, `reconnected`):

1. When the connection drops, fail every pending call at once, and give every stream a `Lost`
   (not `Closed`) so its pane stays and waits.
2. Retry the connection about once a second. Check `hello` again (§6), because the new core may
   be a different version.
3. Subscribe again for a fresh snapshot, which replaces all terminal state.
4. Read every machine's documents again.
5. Reattach every view on the new connection. herdr-app does this without `resumed`, which takes
   the size (§4.3). herdr-frontend should pass `resumed: true`.

Separately, a kept terminal whose program is lost stays live: its stream CLOSEs with the loss
reason. Wait for the `restarted` event and then attach again. While it waits, `send`, `keys`,
`interrupt` and `attach` return `unavailable` (`core:schema/README.md` "Events").

An initial spawn that times out keeps `reason: "spawn_pending"`, and input and attach stay
`unavailable` until it resolves.

### Remote machines

Machines are added to the local core (`machine.add`, CLI `hc machine add`), not dialed by the
client (`core:docs/machines.md`):

- Their terminals appear in the same snapshot and event stream, addressed as `machine/tN`, in the
  same order and under the same filters. `attach`, `get`, `read`, `label`, `kill` and the rest
  take the qualified address, and the local core relays them.
- When a machine's line drops, the relay keeps local attach channels open and reattaches them on
  the same channel, itself using `resumed: true`, when the line comes back
  (`core:crates/herdr-core/src/remote/viewers.rs`). A machine's terminals that changed while it was disconnected
  arrive again as `created`, and those that went arrive as `removed`.
- Pass `on: "<machine>"` to `terminal.run`, `machine.exec`, `file.*` and `doc.*`. A `doc` event
  from a machine carries `machine`.
- Machine line state comes from **polling `machine.list`**, not from events: each machine is
  `connecting`, `connected`, `needs_login`, `needs_update` or `unreachable`, with `since_ms` and
  `why`. herdr-app polls every 2.5 s, and also whenever the terminal list changes
  (`app:src/window.rs:755`). A machine that needs a login retries after 2 minutes, then 5, then
  every 10, and `machine.connect` dials it at once. Calls through a machine that is down fail with
  `unavailable`, `needs_login` or `needs_update`. herdr-app treats `needs_*` as blocked rather
  than retrying on a timer. It reads again on the next `doc` event, `missed`, or reconnect
  (`app:src/mirror_sync.rs` `rpc_error`, `Slot::ready`).
- `temporary: true` machines are agents' sandboxes. herdr-app hides them, along with their spaces
  (`app:src/window.rs` `documents_updated`).

## 2. Methods and events a full client uses

### Methods

Parameters marked `?` are optional. The full schemas are in `hc schema`. herdr-app's minimum set
is `terminal.run, terminal.list, terminal.kill, terminal.label, terminal.attach, terminal.keep,
doc.get, doc.set, events.subscribe` (`app:src/hc.rs:209` `USES`).

| Area | Method | What a desktop client uses it for |
|---|---|---|
| Session | `hello` | The handshake and capabilities (§1.2, §6). |
| | `server.status` | Version, `installed_by` (which updater owns hc), and holders. herdr-app reads it for its updater (`app:src/window.rs` `note_core`). **Never** call `server.stop` or `server.restart` on the user's core. |
| Terminals | `terminal.run {argv?, line?, cwd?, env?, labels?, name?, on?, keep?, size?, display?, parent?, no_parent?, no_notify?, outlive_parent?, rm?, wait?, timeout?, caller?}` | Starting a pane's program. herdr-app sends `env {TERM: xterm-256color, COLORTERM: truecolor, TERM_PROGRAM: herdr}`, `keep: true`, labels `herdr.space`, `herdr.tab` and `herdr.seen=0`, plus `size` (the pane's grid) and `display` (`app:src/hc.rs:471`, `app:src/window.rs:2669`). It returns a `RunResult`, which is the Terminal record plus `output` and `wait` (both only with `wait: true`). When `argv[0]` names a template, the core starts the template's command and sends its body plus the task once the agent is ready. |
| | `templates.list` | Templates (name, description, command) for a "new agent" menu. |
| | `terminal.list {all?, labels?}` | A one-shot list. It is not needed once subscribed, because the snapshot replaces it. Its result also carries `machines` (MachineView). |
| | `terminal.get {terminal, caller?}` | One record, live or finished. herdr-app uses it before adopting a terminal and before deciding a pane's terminal is gone (§3.5). Don't pass `caller` from a UI: it marks a child's news as seen by that parent. |
| | `terminal.kill`, `terminal.rm` | Close a pane, or clear a finished record. |
| | `terminal.keep {terminal, keep}` | Whether a lost program is replaced with a shell in place (never a re-run of the original command). herdr-app keeps every terminal it shows. |
| | `terminal.label {terminal, labels}` | Set `k=v`; `k=` removes the label. Labels are free-form and the core never interprets them (§3.4). |
| | `terminal.read {terminal, lines?}` | The screen plus history as text, without attaching: previews, search, or a launch-failure toast (`app:src/window.rs` `notify_launch_failure`). |
| | `terminal.attach {terminal, cols, rows, history?, display?, observe?, resize_notifications?, resumed?, caller?}` | Framed mode only. Returns `{channel, terminal, resize_notifications, automatic_input}`. The first paint (screen, history, latest status and title, and `CSI ?9001h/l`) is followed by raw output. herdr-app asks for `history: 2000`. See §4. |
| | `terminal.put {terminal, name, data}` | A dropped image or file lands beside the terminal on its machine (up to 8 MB) and returns its path. It types nothing, so the client pastes the path. `put_begin/chunk/finish/abort` are for core-to-core transfers. |
| Agents | `terminal.send {terminal, text, force?, if?, wait?, timeout?, caller?}` | Agent-to-agent messaging: it pastes, then presses Enter after the person's draft is sent or cleared, otherwise after about 3 s of quiet, and refuses `blocked` unless `force`. **Not** for human typing, which goes as DATA on the stream. |
| | `terminal.keys`, `terminal.interrupt` | Named keys, and the stop key. A UI's "stop agent" button maps to `interrupt`. |
| | `terminal.wait {terminal?, children?: any\|all, output?, timeout?, caller?}` | For agents and scripts. A UI watches events instead (§5). |
| Machines | `machine.list`, `machine.add`, `machine.connect`, `machine.rename`, `machine.rm` | Machine management, and line state by polling. |
| | `machine.exec`, `file.read`, `file.write`, `file.edit` (`on?`) | Commands and files without a terminal: git branch and repo info for a space name, or a file viewer, on any machine (`app:src/window.rs` `folder_info`). |
| Documents | `doc.get {name, on?}`, `doc.set {name, value, version, on?}` | The shared layout (§3). |
| Events | `events.subscribe {terminal?, children_of?, labels?, docs?}` | One unfiltered subscription carries every terminal (local and remote) and every document (§2.3). |
| | `rpc.discover` | The schema at runtime, useful for diagnostics. |

### The Terminal record

This is the record from `core:schema/hc.openrpc.json` `Terminal`. Always present: `address,
labels, argv, cwd, state ("live"|"finished"), created_ms, screen ("exact"|"inexact"), cols, rows`.
Optional: `name, pid, parent, keep, rm, notify, die_with_parent, template, identity, title,
status (root Status|null), records {id: Status}, reported, status_ms, turn, foreground {pid, name,
argv, cwd}|null, reason, exit_code, signal, finished_ms, first_message, submit, stop,
paste_gap_ms`.

`Status` is `{state, kind?, progress?, app?, title?, msg?}`, the program's own OSC 7501 record.
`state` is one of `idle`, `working`, `done`, `blocked` or `error`, and `kind` (only when blocked)
is `permission`, `question` or `auth`. The core never infers status from the screen
(`core:crates/herdr-core/src/status.rs`).

`turn` goes up each time the root status leaves `working`. `cwd` is the launch folder, and
`foreground.cwd` is the live one.

The snapshot includes **finished** terminals too; herdr-app filters to `state == "live"`
(`app:src/hc.rs` `EventLines::live`).

### Events

`events.subscribe` in framed mode returns `{seq, terminals, channel}`. Events arrive on that
channel as newline-delimited JSON-RPC notifications without an id, and DATA frame boundaries can
fall anywhere inside a line (`app:src/hc.rs` test
`document_and_missed_events_survive_arbitrary_frame_boundaries`).

- `event {seq, type, terminal?, machine?, data}`: apply it only when `seq` is above the last seq
  applied.
- `heartbeat {seq}`: sent every 15 s when nothing else is queued.
- `missed {seq, terminals}`: a fresh snapshot. Replace everything, drop events whose seq is not
  above it, and read the documents again.

How to apply each event type (`core:schema/README.md` "Events"; `app:src/hc.rs` `EventLines::apply`):

| type | data | apply |
|---|---|---|
| `created` | the whole Terminal | Add it, or replace it (a remote machine reconnected). |
| `lost` | `{reason, exit_code, signal, finished_ms: null}` | It stays `live`: set these fields, clear `pid`, drop `foreground`. Its attach stream has closed; wait for `restarted`. |
| `restarted` | the whole Terminal | Replace it and reattach. |
| `keep` | `{keep}` | Set it. |
| `finished` | `{reason, exit_code, signal, finished_ms}` | Set these fields, set `state = "finished"`, and drop `foreground`. A `status` event clearing the status comes just before it. |
| `removed` | `{}` | Drop it. |
| `status` | `{status, records, reported}` | Replace all three. |
| `turn` | `{turn, state}` | Set `turn`. This is where seen and done decisions happen (§3.4). |
| `title` | `{title}` | Set it. |
| `labels` | `{labels, record?}` | Replace the labels. With `record`, the terminal newly matches a label filter: add it. |
| `size` | `{cols, rows}` | Set both. This is the only size news a non-observe viewer gets (§4). |
| `foreground` | `{pid, name, argv, cwd}` or null | Set it. The core samples about twice a second and emits on change. |
| `doc` | `{name, version}`; no `terminal`, plus `machine` when remote | Read that document with `doc.get` (and `on: machine`) when the version is newer than yours. |

`seq` rises by one per event and restarts with each core process. A remote stream's `missed`, and
each (re)establishment of a machine's subscription, reaches local unfiltered and document subscribers as a
local `missed`.

A `docs: [...]` filter (since 0.1.22) narrows the document events. Naming documents and nothing
else gives an empty terminal list. Terminal, parent and label filters exclude document events. A
full client wants no filter.

Plain mode works too: after `events.subscribe`, that connection carries only notifications. A
plain subscriber more than 1024 events behind gets `missed`, and one that stops reading for 30 s
is dropped (`core:crates/herdr-core/src/server.rs` `plain_events`). Framed mode is what herdr-app uses.

## 3. State shared with Herdr app

### What lives where

| State | Owner and location | Shared? |
|---|---|---|
| Terminals, their programs, status, turn, title, size, foreground | The core's registry | All clients |
| Labels | The core, on each terminal; they end with it | All clients (§3.4) |
| Spaces → tabs → split trees | Document `herdr-app` **on each machine's core** (`app:src/mirror.rs` `Document`, `app:src/mirror_sync.rs:77`) | All clients on any core that can reach that machine |
| Active space, each space's selected tab, each tab's focused pane, focus history (`before`), zoomed pane, `settled` (put away), recently closed spaces, the local seen fallback (`attention`) | herdr-app's `~/.config/herdr-app/view.json` (`app:src/mirror.rs` `View`) | **Private to this screen** (test `focus_zoom_and_settle_are_private`) |
| Window chrome layout, theme, keys, mods, settings, window position | herdr-app home (`layouts/*.json` plus `.state`, `settings.json`, `window.json`, `mods/`) | Private to herdr-app. herdr-frontend has its own. |

herdr-frontend must not read or write herdr-app's home. It keeps its own equivalent of `View`.
For state that herdr-frontend's own screens share with each other, use a separate document such
as `herdr-frontend`. Labels are for small values that every Herdr client shares, and they use the
`herdr.` prefix. State for one device stays on that device (`app:docs/labels.md` "Adding more").

### The `herdr-app` document

The live local copy was version 458: 20 spaces in 9.9 KB. Documents can be up to 1 MiB. The
schema is herdr-app's serde types (`app:src/mirror.rs`, `app:src/layout.rs`):

```jsonc
{ "spaces": [ {                       // order inside a machine is shared
    "id": "sp<32 hex>", "name": "",   // "" = named after the first terminal's checkout
    "folder": "/Users/me",            // where new terminals in the space start
    "tabs": [ {
      "id": "tb<32 hex>", "name": "", // "" = called by its position (1, 2, …)
      "root": {                       // a Node; the root's id equals the tab's id; normally a row
        "id": "tb<…>", "type": "row", // "row" | "column" | "stack" | "block"
        "children": [
          { "id": "p<32 hex>", "type": "block", "content": { "terminal": "t6p" } },
          { "id": "s<32 hex>", "type": "column", "size": { "weight": 1.0 },
            "children": [ /* … */ ] } ] } } ] } ] }
```

- A machine's document holds **only that machine's** spaces, with ids and terminal addresses
  unqualified (`t6p`, not `devbox/t6p`). In memory, herdr-app qualifies them as `devbox/sp…` and
  `devbox/t6p` (`app:src/mirror.rs` `qualify`/`local`/`map_node`). Spaces show grouped by machine:
  this machine first, then the others by name (`app:src/model.rs` `order_spaces`). Moving a space
  stays inside its machine's group.
- Ids are a prefix (`sp`, `tb`, `p`, `s`) plus 128 random bits in hex. They must never be a
  per-screen counter (`app:src/model.rs` `fresh_id`, test `fresh_ids_are_not_a_per_screen_counter`).
- Each Node has `id` and `type`. Blocks have `content`; containers have `children`. The other
  fields are optional: `size` (`{px}` or `{weight}`), `min`, `max`, `hidden`, `title`, look
  fields, `floating`, stack `active` and `header`, and so on (`app:src/layout.rs` `Node`). Block
  `content` is untagged: `{terminal}`, `{mod, props?}` (a herdr-app JS mod), `{tab, pane?}` (in
  chrome layouts), or `{agent}`. The live document used only `row`, `column`, `block` with a
  terminal, and `size.weight`.
- **Split sizes are shared**: `size` lives in the tree, so a divider dragged on one screen moves
  on the other.
- Every shared field has a serde default, so `{"spaces":[{"id":"s","tabs":[{"id":"t"}]}]}` decodes
  (test `shared_fields_can_be_omitted`). An unknown `type`, or a `content` matching none of the
  variants, fails to decode. herdr-app then marks the machine's layout "unavailable" and stops
  writing it (`Outcome::Undecodable`).

### Concurrency and versioning

- The core gives one version per document name. `doc.set` succeeds only at the current version
  and returns the new one. A stale write fails with `conflict` and message
  `document "x" is at version N, not M`. Writing `null` deletes the value but keeps the version.
  An unwritten name reads as `{value: null, version: 0}`. Writes persist atomically and emit a
  `doc` event (`core:crates/herdr-core/src/api/doc.rs`).
- How herdr-app uses it (`app:src/mirror_sync.rs`, `app:src/window.rs:2067` `flush_documents`,
  `:2144` `documents_updated`):
  - It keeps one slot per machine and at most one request in flight per machine. There is no
    queue of operations: each round sends the latest projection of the model.
  - It writes only when the projection differs from the last document it read or wrote. It
    doesn't write while a pane is being dragged, and it finishes pending writes before quitting.
  - On `conflict` it reads the document again and **replaces its model with the other screen's
    copy, discarding its own unsent edit**, with the toast "Layout changed elsewhere".
  - A read that changes nothing triggers no write.
- So the first writer wins: herdr-app never overwrites a newer version. herdr-frontend must
  follow the same CAS discipline, and it can do better on conflicts:
  1. Keep the last document and version read for each machine.
  2. When the person edits, apply the edit to the local model, project it, and `doc.set` at the
     known version. Keep one request in flight per machine and coalesce edits made meanwhile.
  3. On `conflict`, `doc.get`, then replay the *intent* on the fresh copy: split this pane, close
     that tab. Drop the intent if its target is gone, and retry a bounded number of times.
     Replaying is what avoids herdr-app's discard-and-toast.
  4. On a `doc` event, `missed`, or reconnect: `doc.get` and replace that machine's part of the
     model, reapplying this screen's private view where its ids still exist (as
     `View::apply_machine` does).
  5. **Never write in reaction to a read.** Write only for an edit someone made. If
     herdr-frontend normalized documents differently from herdr-app (field order, defaults,
     floats, ids), "fixing" them on read would ping-pong writes between the two clients forever.
- **Preserve what you don't understand.** herdr-app decodes into typed structs. Since 0.1.15 it
  keeps unknown fields on a *space* or *tab* (`rest`, flattened) and writes them back, so a newer
  build's additions survive an older build's write (`app:src/mirror.rs` `SharedSpace`/`SharedTab`,
  test `unknown_space_and_tab_fields_survive_a_read_and_write`). It still drops unknown fields on
  the document root and on every `Node`, and it can't decode unknown node `type`s or `content`s.
  So:
  - herdr-frontend should carry everything it doesn't understand through untouched (keep the raw
    JSON beside the typed view), at every level, so a newer herdr-app's additions survive
    herdr-frontend's writes.
  - A field herdr-frontend adds survives herdr-app (0.1.15 and later) only on a space or a tab.
    Builds before 0.1.15 drop it there too. Put any such addition there, and only one both apps
    agree on.
  - Draw mod blocks as placeholders, and never drop or rewrite them when writing the document.
    Whether a person may close one is open question 2.

### Labels

Labels are free-form `key=value` and the core never interprets them. `terminal.label` with `k=`
removes `k`. Each `labels` event carries the whole map. These are the conventions, from
`app:docs/labels.md` and from what herdr-app writes in `app:src/window.rs`; the last four are not
in `docs/labels.md`. On the live core, 31 of 33 terminals had `herdr.space`/`herdr.tab`, 27 had
`herdr.seen`, and 32 had `where`.

| Label | Meaning | Writer |
|---|---|---|
| `herdr.seen=<turn>` | The last turn a person looked at, on any client. | See the rules below. Every new terminal a client starts gets `0`. |
| `herdr.pinned=1` | Pinned; pinned agents sort first. Unpin with `herdr.pinned=`. | A person's action (`app:src/window.rs:3457`). |
| `herdr.space=<id>` | The space it belongs to (an unqualified id on its machine). Terminals started elsewhere (agents, scripts) opt into the window with it (`app:src/SKILL.md`). | `terminal.run`; set again on "keep in a pane"; cleared (with `keep=false`) on "park" (`app:src/window.rs:2898` `start_terminal_change`). |
| `herdr.tab=<id>` | Its tab within that space. Without it, herdr-app creates a new tab. | As above. |
| `where=<space name> / <tab name>` | A human label shown by `hc ls` and hc's picker. Sub-agents inherit their nearest placed ancestor's. | herdr-app, whenever the value changes (`app:src/window.rs:2018` `write_where`). |
| `herdr.right-click=program` | Right-click goes to the program instead of the pane menu. | A person's action (`app:src/window.rs:3441`). |

`herdr.seen` rules (`app:docs/labels.md`; `app:src/window.rs:1717` `share_seen`;
`app:src/model.rs` `status`):

- Shown state: `blocked` or `error` means **needs you**; `working` means working. Any other word
  means **done** when `turn > herdr.seen` and idle otherwise. With no label, the client's own seen
  rule applies; a missing label is not 0.
- Write `herdr.seen=<turn>` only when a person is really looking: the window is in the foreground
  and the agent is drawn on screen (a peek counts, a covered pane doesn't). Write once per turn
  while it stays on screen, only ever raise the value, and also write when the label is missing.
  Make the decision on the `turn` event; the `status` event comes first.
- Mark unread is the only lower write: `turn - 1`, and only when `turn > 0`. The last writer wins.
- herdr-app tracks the highest `herdr.seen` that went by in each batch of events. That way its
  own raise isn't hidden by another client's later, lower "mark unread" in the same batch
  (`app:src/hc.rs` `note_seen`, test `a_seen_write_stays_known_under_a_later_lower_one`).

### How herdr-app reconciles the layout with the core's terminals

These rules run inside herdr-app and act on whatever herdr-frontend writes.

- **Adoption.** On every listing, a live terminal with a non-empty `herdr.space` that no pane
  shows gets placed. This only happens once that machine's document is available, and only after
  `terminal.get` confirms the terminal is still live with the same labels. If it isn't kept,
  herdr-app sets `keep=true`. It goes into the labeled tab (a split right of its last pane), else
  a new tab in the space, else a new space under the labeled id. Then herdr-app writes the
  document (`app:src/window.rs:2420` `reconcile`, `start_adoption`, `adopt`, `adoptable`).
  Consequences for herdr-frontend:
  - When it starts a terminal for a pane, it must label it and also put it into the document,
    exactly as herdr-app does. Otherwise herdr-app places it elsewhere.
  - If both clients place the same terminal, the CAS loser must check `pane_of(address)` on the
    fresh copy before replaying, or the terminal appears twice.
  - To show a terminal outside the layout, don't give it `herdr.space`. Unlabeled workers stay
    hidden.
- **Closed panes.** herdr-app removes a pane when its attach stream ends with reason `exited`,
  `killed` or `finished`. It also removes a pane whose terminal is missing from the live list once
  `terminal.get` reports `reason` `exited` or `killed`, or `not_found`. Terminals that this herdr-app
  started less than 5 s ago are spared (terminals other clients start get no such grace) (`app:src/window.rs` `terminal_ended`, `:2813` `check_closed`, `:2828` `checked_closed`, `just_born`). Both
  clients may remove the same pane; under CAS that converges. Never put an address into the
  document before `terminal.run` has returned it.
- **Close vs park.** Closing a pane or tab kills its terminals.
  - On cores 0.1.13 and later, herdr-app kills only those terminals. The core then ends every live
    child with `die_with_parent` (set at start as `parent && !outlive_parent`, never changed)
    when its parent finishes, **including children shown in their own pane or labeled
    `herdr.space`** (`core:crates/herdr-core/src/notes.rs` `Job::Orphaned`,
    `core:crates/herdr-core/src/api/run.rs`). Only `outlive_parent` children survive.
  - On older cores, herdr-app walks down the tree and kills the children itself. That walk, and
    the explicit kill command's walk on any core, spares children shown in a pane or labeled
    `herdr.space` (`app:src/window.rs` `close_terminals`, `kill_tree`, `kill_targets`;
    `app:src/hc.rs` `legacy_child_lifetime`). On a new core the sparing doesn't protect them,
    because the core still ends `die_with_parent` children.
  - Parking takes the pane out of the layout but keeps the program running: herdr-app clears
    `herdr.space` and `herdr.tab` and sets `keep=false`.
  - herdr-frontend should implement both with the same label effects. To keep a placed
    sub-agent alive past its parent, it has to have been started with `outlive_parent`.
- **`where`.** herdr-app computes the space name from the space's name, or from the first
  terminal's git checkout top or folder, plus the tab's name or index. If herdr-frontend computes
  it differently, the two clients overwrite each other's label forever. Version 1 should leave
  `where` to herdr-app, or match `Model::space_name` and `Model::tab_name` exactly (see Open
  questions).
- **Space names.** An unnamed space (`name: ""`) is displayed under the first terminal's checkout
  name. This is computed per screen and never written.

## 4. Terminal sizing

### Who owns the PTY size

From `core:crates/herdr-core/src/viewers.rs:70` (`attach`), `:287` (`touch`) and `:387` (`apply_size`), and checked
with the probe:

- A terminal has **one** grid. The size comes from the non-`observe` viewer with the latest
  `active_at`. A viewer becomes active when it **attaches** (unless `resumed: true`), sends DATA
  (human input), sends RESIZE (even with an unchanged size), or sends FOCUS(1). AUTOMATIC_INPUT,
  FACTS and FOCUS(0) are not activity. That leader's `Display` facts also answer the program's
  color and cell queries.
- `resumed: true` attaches with `active_at = None`, so the viewer takes the size only once it
  becomes active. If *every* non-observe viewer is `None`, `max_by_key` picks the last one
  attached. In other words, resumed viewers tie, the last attached wins, and any viewer that has
  been active beats them.
- `observe: true` viewers never type, never resize, and their query replies never reach the
  program. They can opt into `resize_notifications: true`: the reply confirms it only if every
  hop on the path supports it. The observer then receives RESIZE with the real grid before its
  first paint, and on every change RESIZE followed by an authoritative repaint (starting with
  CAN), in stream order. RESIZE uses no credit.
- When the leader detaches, the next most active viewer's size applies. With no non-observe viewer
  left, the terminal goes to the **headless size, 200×120 by default** (`apply_size`'s
  `self.headless()`). `terminal.run {size}` sets the size before the program starts.
- Each change emits a `size` event `{cols, rows}`. A non-observe viewer that isn't the leader gets
  **no** in-band notice; it must follow `size` events. Those arrive on the events channel, so they
  are not ordered with its stream bytes.
- Programs learn the size through SIGWINCH (via the holder). Mode-2048 programs wait for an
  in-band report that the viewer's VT produces after the resize: herdr-app sends
  `vt.take_replies()` as AUTOMATIC_INPUT right after RESIZE (`app:src/terminal.rs:262` `fit`).

### Recommended viewer policy for herdr-frontend

| Pane state | Attach | Sends |
|---|---|---|
| Focused, in the focused window | Normal attach | When it becomes active (FOCUS(1), the first key typed, or its tab shown with focus): RESIZE with the pane's current grid, sent before or with that frame. FOCUS(1) on its own would apply the size this viewer last reported, which may be stale. Then RESIZE on every geometry change, DATA for keys, and FOCUS(0) on losing focus. |
| Visible but not focused, or focused while the window is in the background | `resumed: true` | Nothing that takes the size. It draws at the core's grid from `size` events, letterboxed or clipped inside the pane, until the person types into it or focuses it. It doesn't follow window or divider changes either, even when herdr-frontend is the terminal's only viewer: that is the price of never stealing the size. |
| Hidden (another tab), but kept attached so tab switches are instant and images survive | `resumed: true`, or `observe: true, resize_notifications: true` when it never needs to answer queries | Nothing. An observer gets exact RESIZE plus repaint pairs. |
| Reattach after a dropped connection | `resumed: true` | Nothing until it is really used again. |

Avoid detaching hidden panes just to save resources. If no other viewer is attached, that sends
the program to 200×120 and back on every tab switch.

There is no "take size" call, and a viewer can't switch between observe and active without
reattaching. "Take size" is simply sending RESIZE with the pane's grid.

### What herdr-app does that causes wrong sizes

herdr-app never uses `observe`, `resumed` or `resize_notifications`, and it never follows `size`
events for its own views: its only read of `cols`/`rows` is the size hint used before the first
attach (`app:src/window.rs:1597`). With both clients on one terminal:

1. **It attaches every pane's terminal, in every tab, as an active viewer, as soon as the pane
   appears in the document**, including panes herdr-frontend adds (`app:src/window.rs` `sync`:
   "Every tab's terminals stay attached"). Panes in herdr-app's shown tab attach at herdr-app's
   pane grid, which changes the size. Panes in hidden tabs attach at the record's current
   `cols`/`rows` (`app:src/window.rs:1597`), so the size doesn't change, but herdr-app becomes the
   leader.
2. **It resizes hidden tabs once per window geometry.** When its window or cell size has settled
   (the same for two ticks), `fit_hidden_tabs` sends RESIZE for terminals in tabs it isn't
   showing, but only where herdr-app's own grid for them differs (`app:src/window/pane_size.rs:202`,
   the `HiddenFit::Done` guard; `app:src/terminal.rs:262` `fit`). So about a second after
   herdr-app starts, and again after each of its window or zoom changes, every hidden terminal
   moves to herdr-app's geometry, though nobody is looking at it there.
3. **It reattaches without `resumed`** after a reconnect (`app:src/window.rs:911` `reconnected`
   → `TerminalView::reattach`). Every core restart or update moves every terminal to herdr-app's
   pane sizes.
4. **It draws at its own pane size when it isn't the leader.** Its VT stays at the pane's grid
   while the PTY runs at the leader's, so its picture of a terminal that herdr-frontend leads
   wraps wrong, until herdr-app types, focuses or resizes and takes the size back.
5. FOCUS(1) whenever a herdr-app terminal gains keyboard focus, including window activation,
   takes the size. Since 0.1.15, a mouse-down in a herdr-app terminal also re-sends RESIZE with
   its grid ("reclaim terminal size when returning to a pane", `0ac92e4`). Panes that leave the
   screen send FOCUS(0) (`TerminalView::blur`). All of this is correct behavior, and it is the
   same "take size on real use" rule that §4.2 recommends.

The upshot: with both apps open, a terminal's size flips to whichever client touched it last.
herdr-frontend can't prevent herdr-app's takeovers (items 1–3). It can avoid causing takeovers
itself (§4.2) and draw at the real grid (item 4), so it never shows a misdrawn screen. Items 1–4
are worth raising upstream for herdr-app: use `resumed` for hidden and reattached views, don't
`fit` hidden tabs, and follow `size` events.

## 5. Agent orchestration features

- **Status.** OSC 7501 (the Program Status Protocol) reports from the program, stored verbatim:
  a root `status`, extra `records` by id, `reported`, and `status_ms`. `turn` counts each time
  the status leaves `working`. A program that never reports has no status, and `wait` treats it
  as working until it exits (`core:crates/herdr-core/src/status.rs`).
- **The attention model** (herdr-app's, which herdr-frontend should match;
  `app:src/model.rs` `status`, `alert`, `alert_for`, `priority`). In herdr-frontend this drives
  in-app UI only: sidebar status, attention markers, and in-app toasts like Eli's `eli-toast` mod.
  Native OS notifications and sounds are out of scope.
  - Displayed status is blocked (blocked or error), working, done (turn > seen), or idle. Tabs and
    spaces roll up by the priority blocked > done > working > idle.
  - When to raise an in-app toast: entering blocked or error always does. Going from busy to
    anything else does only when the person isn't looking.
  - Only terminals in a pane raise one. Sub-agents (`parent` set) never do; their root agent
    stands in for them. Raising one also brings the root agent's settled tab back.
  - herdr-app also plays a sound when sounds are enabled in its settings (`app:src/window.rs`
    `alert`). Eli has them off, and herdr-frontend leaves them out. Each app's toasts show only in
    its own window, so running both at once doesn't duplicate anything on screen.
- **Parents and children.** A terminal started from inside a terminal gets `parent`, which is set
  once. Children end with their parent unless `outlive_parent`. The core types notes about a
  child (turn ended, blocked, error, exit) into its parent agent as `<hc from="t7 name">…</hc>`
  unless `no_notify` or config `notes = false` (`core:crates/herdr-core/src/notes.rs`). `notify` on the record says
  whether that happens.
  - Sends and notes wait while a person has an unfinished draft: up to `draft_wait` (default
    60 s) after their last key, otherwise about 3 s of quiet (`core:crates/herdr-core/src/SKILL.md`). The core
    knows a draft only from DATA frames, so human keys must be DATA and VT replies
    AUTOMATIC_INPUT. Otherwise either drafts are missed or replies count as typing.
  - A UI can show teams with `events.subscribe {children_of}`, or by grouping on `parent` from
    the main stream. herdr-app gives sub-agents the `where` of their nearest placed ancestor.
  - `parent` on a remote or cross-machine record may name its machine by that core's **host name
    or core id** (`host-alpha/t4`, `alpha-id/t4`) instead of this core's name for it, or name
    this machine itself. Since 0.1.15, herdr-app normalizes `parent` before using it. A prefix
    that is this core's `hello.core.id` or `core.name` means a local `tN`. Otherwise it maps
    through `machine.list` by `name`, then `id`, then a unique `host` (`app:src/hc.rs`
    `EventLines::live_for`, test `parent_addresses_match_the_viewing_cores_terminal_addresses`).
    herdr-frontend must do the same before matching parents to terminals.
- **Waiting and messaging.** `terminal.wait {children: any|all}`, `terminal.send {wait}`,
  `terminal.keys` and `terminal.interrupt` are agent tools. A UI needs only `interrupt` (stop) and
  perhaps `send` (a "message this agent" box). A UI waits by watching events, never with
  `terminal.wait`.
- **Templates.** `templates.list` provides roles. `terminal.run {argv: [template, task…]}` starts
  one and reports `first_message {sent, started, turn, reason}`. If it wasn't sent, the record
  keeps the reason.
- **`foreground`.** The process running in the terminal now and its folder. herdr-app uses it to
  pick program icons and to follow folders (`app:src/window.rs` `running_argv`, `track_folders`).

## 6. Version compatibility and capabilities

- **Generation.** Protocol generation 1. A real break needs a new generation. The API only grows:
  `core:schema/released.openrpc.json` is the last release, and a test fails on any change that
  would break its clients (a removed method, parameter or result field, a new required input, an
  input that accepts less, or a new kind of answer) (`core:schema/README.md`).
- **Unknown parameters are ignored** by released cores, including when forwarded to another
  machine (`app:src/hc.rs` comment in `run`; probe: `terminal.get {bogus: 1}` succeeds). Sending a
  newer optional parameter to an older core is therefore safe, but it may silently do nothing.
  When the effect matters, gate on a feature or version.
- **Features.** `hello.features` covers what can't be seen from method names, and the attach reply
  confirms that every hop on the path supports a feature:
  - `automatic_input` needs both the feature *and* `attach.automatic_input == true`; otherwise send
    DATA.
  - `resize_notifications` needs both the feature *and* `attach.resize_notifications == true`;
    otherwise follow `size` events.
  - If a relay loses a feature on reconnect, the stream closes; attach again to negotiate.
- **The check herdr-app makes** (`app:src/hc.rs:256` `check`): if `generation` is above 1, the app
  needs an update. If it is below 1, or `version` is below the minimum (`distribution/core-version`,
  currently `0.1.11`, compared as numeric semver), the core needs an update. If any method in
  `USES` is missing from `hello.methods`, the core needs an update.
- **Remote machines.** `machine.list[].version` is each machine's hc version when last seen. A
  machine speaking another generation shows as `needs_update` (`incompatible` when dialing), and
  calls through it fail with `needs_update` ("hc machine update <m>"). Old remote cores lack newer
  methods. herdr-app turns `needs_update` and `needs_login` on `doc.*` into a "Layout unavailable"
  notice and doesn't retry on a timer, only on the next `doc` event, `missed`, or reconnect.
- **Recommended minimum for herdr-frontend: hc 0.1.22.** It is what's installed here, and it is
  the first version with the `docs` subscription filter and the reconnect-size fix. Everything
  else the design uses arrived earlier: `size`/`display` on `terminal.run` (0.1.18),
  `automatic_input` (around 0.1.18), and observe `resize_notifications` (0.1.17)
  (`core:CHANGELOG.md`). Only require what the code actually calls, and degrade by feature flag.

## 7. Recommended Rust client design

herdr-frontend is a native desktop app on Rune (anomalyco/rune, a GPU-rendered Rust UI framework
built on wgpu, Taffy and Parley). Its sidebar, tabs, popups, palette and toasts are native Rune
elements, and each terminal pane is a GPU-rendered view inside the window, as in Herdr app.
The client crates below stay independent of the UI toolkit. Rune's runtime and threading model is ticket
004, so the client exposes channels and a wake hook and doesn't assume an executor. It follows
herdr-app's proven shape (two threads per connection, routes behind a mutex, no async runtime in
the client), but with typed messages and the fixes above.

### Threading

- Each connection runs a reader thread (decode frames, route replies to a oneshot per id, route
  stream frames to per-channel channels, and never block, as herdr-app's `try_send` doesn't), a
  writer thread (it drains a frame queue, so a core that stops reading never blocks the UI), and,
  for `hc connect`, a stderr thread that keeps the startup error.
- Blocking `call` must never run on the UI thread. `Pending<R>` supports both `.wait()` (for
  worker threads) and `Future` (for whatever executor Rune provides). Default timeout is 10 s, as
  in herdr-app. On timeout, send `$/cancelRequest` and drop the route.
- One events pump (a thread or task) applies notifications to `TerminalSet`, returns credit after
  parsing, and posts coalesced `Changes` to the UI through a wake hook. Don't poll every 500 ms
  like herdr-app does: post as soon as events arrive.
- One worker per machine runs `Mirror` rounds (`doc.get`/`doc.set`), with at most one in flight
  per machine. A per-terminal reader feeds VT bytes to the renderer, which returns CREDIT after
  `write`.
- The supervisor owns reconnect. Every handle carries the connection generation, so results from
  an old connection are ignored, as herdr-app's `core_generation` guards do.

## Probe

`/tmp/hfr001/probe/probe.py`, throwaway and not committed. It ran against an isolated core
(`HC_SESSION=test-hfr001` with scratch XDG dirs, stopped afterwards), with two framed connections
A and B on one `sh -c "sleep 600"` terminal started at `size 90×20`:

| Step | Size after |
|---|---|
| A attaches 80×24 | 80×24 |
| B attaches 100×30 | 100×30 (the last attach leads) |
| A sends RESIZE 81×24 | 81×24 |
| B sends FOCUS(1) | 100×30 (gaining focus is activity) |
| A sends AUTOMATIC_INPUT | 100×30 (not activity) |
| C attaches 120×40 with `resumed: true` | 100×30 (doesn't take the size) |
| O attaches 50×10 with `observe: true, resize_notifications: true` | 100×30. O's first frames were RESIZE 100×30, then the paint. |
| B sends CLOSE (the leader leaves) | 81×24 (back to A). O received RESIZE 81×24, then a repaint. |

Other results:

- The attach reply had `automatic_input: true` and `resize_notifications: false` (A wasn't an
  observer).
- `doc.get` on a new name returned `{value: null, version: 0}`. `doc.set` at version 0 returned

## Open questions

These need decisions in later tickets.

1. **The `where` label.** Leave it to herdr-app (version 1), or port `space_name` and `tab_name`
   exactly, including the git checkout-top lookup.
2. **Mod blocks** (`{mod, props}`) in shared documents can't run in herdr-frontend. They need a
   placeholder design, and herdr-frontend never drops or rewrites them on write (§3.3). Still
   open: whether a person may close one from herdr-frontend, which removes it for herdr-app too.
3. **Upstream fixes to herdr-app's sizing** (§4.3, items 1–4), so that using both side by side
   doesn't flip sizes. This is for the herdr-app maintainers to decide, not this repo.
4. **`TERM_PROGRAM`.** Should herdr-frontend's terminals identify as `herdr`, as herdr-app's do,
   so programs behave the same whichever client started them? This depends on ticket 003's VT
   choice.
